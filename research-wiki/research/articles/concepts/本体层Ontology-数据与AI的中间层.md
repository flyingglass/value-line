# 本体层（Ontology）：数据与 AI 之间的决策中间层

> 收录日期：2026-09-20

## 一、定义

**Ontology（本体层）**：把组织里散落在各处的真实事物（卡车、订单、病人、士兵、机器）及其关系，用一套**统一的"业务语言"**映射到软件里，让人类和 AI 都能看懂、并能直接下达动作。

三个身份定位：

| 说法 | 出处/语境 |
|---|---|
| **"连接数据和 AI 的中间层"** | 既不是数据，也不是大模型 |
| **"一个决策系统"** | Palantir 管理层口径（作者转述） |
| **"翻译官"** | 把机器看得懂的语言，翻译成人和智能体看得懂的"人话" |

> 在"翰林 vs 县令"的语境里：**本体就是帮助大模型由翰林变成县令的东西**。

## 二、本体装的两样东西

### 1. 语义元素（"名词"）

| 元素 | 含义 | 例子 |
|---|---|---|
| **对象** | 现实世界的实体 | 员工、飞机、采购订单、威胁行为者 |
| **属性** | 对象的字段 | 员工姓名、油井经纬度 |
| **链接** | 对象之间的逻辑关系 | "员工向经理汇报"、"发票包含明细项" |

### 2. 动力学元素（"动词"）

| 元素 | 含义 | 例子 |
|---|---|---|
| **动作** | 可对对象执行的操作 | "批准采购订单"、"派遣技师" |
| **函数** | 封装好的业务逻辑 | "计算资产利用率" |
| **安全** | 谁在什么条件下能看什么、改什么 | 约束结果 |

## 三、与 BI / 看板的分界线：能不能"写回"

> **大多数 BI（经营分析）工具只能"读"数据，而本体的动作可以"写回"到底层系统去执行。**

对照示例（医疗制造商，底层几百个数据源：ERP、供应链、物流跟踪、产线传感器）：

| | 没有本体 | 有了本体 |
|---|---|---|
| 状态 | 数据孤岛、表结构混乱；生产工程师看工单表、仓库员看库存表、供应链分析师看物流表，**三者对不上话** | 统一映射为业务对象："生产工厂"、"工单"、"客户"、"入库包裹"、"出库货件" |
| 飓风来袭时 | 弹个天气图，"**剩下的你自己想办法**" | 说一句"重新规划所有经过厦门的货车路线" → Agent 理解业务关系 → 自动算新路线 → **直接发指令给 SAP 更新运单** |

关键：**本体把"对象 + 状态 + 允许的动作 + 执行权限"都建模好了，AI 才真正能动手**。

## 四、语义翻译的机制（原文示例）

```
数据库行：  ID_9982, Status_0, Loc_NY         ← 对机器友好，对人/AI 不友好
                    ↓ 本体做语义翻译
业务语言：  卡车 9982 · 油箱为空 · 当前在纽约   ← 人和 Agent 都能直接用自然语言操作
```

## 五、数字化 vs 数智化（本体的位置）

| | 含义 |
|---|---|
| **数字化** | 把企业组织方方面面的要素，在数字孪生中生成一个映射（原子 → 比特） |
| **数智化** | 在数字世界复刻一个**能自我完成任务、甚至做一些不太重要决策**的数字孪生；让 Agent 读懂数据 + 读懂数据之间的**业务勾稽关系** |

**企业级 AI 应用的三个前提**：① 完成数字化；② 让 AI 读懂这些数据在企业语境中的含义；③ AI 可基于这些数据做推理和决策。

→ **Palantir 做的是第 ②③ 件事**，前提是"已经完成数字化的美国企业"。

### 数字化的四阶段（按被数字化的时间顺序）

1. **文件文档**：纸质 → Word / Excel / PPT / PDF / CAD 图纸
2. **沟通方式**：QQ、微信等即时通讯
3. **业务信息**：SAP ERP、Salesforce CRM（进销存、财务、销售跟进）
4. **组织与流程**：OA、钉钉（组织架构、审批流程、汇报与协作关系）

原文强调这是**循序渐进**的过程，且存在梯度：**大企业 > 小企业；美国企业 > 中国企业**。

## 六、投资筛选标准（可直接用）

原文结论：

> **避开那些工具型的 SaaS，去找到那些干本体活儿的公司。但不一定要像 Palantir 那么大而全的，只要是在某个细分领域，能够让大模型理解具体业务，让 Agent 跑起来干活儿的就行。**

三条判据：

| # | 判据 | 反面（要避开的） |
|---|---|---|
| 1 | **干"本体活儿"**：数据治理 + 数据映射 + 灌入行业 know-how + 工作流与汇报关系 | 躺在那里等人用的**工具型 SaaS** |
| 2 | **不必大而全**：细分领域能让 Agent 跑起来干活即可 | 只有"AI+"概念、无具体场景 |
| 3 | **+AI 而非 AI+**：场景来自产业深耕 | 大厂出来的创业者带着消费互联网思维做 AI+ |

**暴论（原文）**：短期投资机会**不在于创业公司，而在于"在产业田间地头深耕的公司"**。

判据 2 很重要：它把门槛从"复制 Palantir"降为"**在某细分领域建成可用的本体**"——这降低了"Palantir 在中国不可复制"这一否定判断的力度。

## 七、与本库"AI To B 平台类 pass 记录"的关系

用户此前 pass 国内 AI To B 平台类的理由是"项目制手写定制代码、无 Ontology 产品化沉淀、毛利低"。本篇提供了**更精确的筛子**：

- 不改结论，但把判据从"是不是项目制"换成更可观测的：**有没有建成可复用的本体层（对象/关系/动作建模）**、**动作能否写回底层系统**、**是否只在细分领域成立**（细分领域成立也算数）
- 对应的可观测信号：产品里是否暴露"对象类型 + 关系 + 可执行动作"的建模界面；客户案例里是否出现"Agent 直接改写 ERP/MES/WMS"而非只出报表

## 八、局限 / 待核

- 全篇**定性判断、无财务数据**，来源为个人投资随笔
